# Статический SPA без фреймворков: как устроен Ayurveda Reader

Когда говоришь «статический сайт на чистом JS», обычно представляют лендинг на пару страниц. Но Ayurveda Reader — это полноценное одностраничное приложение с 34 541 шлоком (стихом) из семи классических аюрведических текстов, поиском по всему корпусу, рендерингом санскрита в деванагари и IAST, тестом из 60 вопросов, 208-статейной энциклопедией и Telegram-ботом на той же машине. Без React. Без Vue. Без SSR. И это не ностальгия по 2010-м — это осознанное архитектурное решение.

В этой статье расскажу, почему мы так сделали, что получилось хорошо, что пришлось решать нетривиально и какие грабли ждут тех, кто пойдёт тем же путём.

---

## Почему не фреймворк

Когда проект только начинался, вопрос «брать React или нет» встал буквально в первый вечер. Я прошёлся по стандартным аргументам:

**За фреймворк:** компонентная модель, экосистема, hot reload, state management из коробки, удобнее нанимать людей.

**Против:** оверхед bundle-а для контента, который почти весь статический; сложность SSR для SEO; зависимость от npm-экосистемы с её ломающимися обновлениями; и главное — большая часть «динамики» на сайте — это просто показ/скрытие блоков и загрузка JSON.

Когда большинство интерактивности сводится к `fetch()` + вставка HTML через `innerHTML` или шаблонные строки — фреймворк добавляет сложность, а не убирает её. Мы остановились на ванильном JS.

## Архитектура: SPA на якорях

Приложение работает как SPA через `hashchange` — навигация реализована через `window.location.hash`. Каждый «экран» — это отдельный модуль JS, который рендерит содержимое в корневой `div` при изменении хеша.

```
index.html
├── style.css
├── data.js           — индекс всех модулей
├── library.js        — список текстов, навигация по главам
├── charaka-data.js   — шлоки Чараки (~8K)
├── sushruta-data.js  — шлоки Сушруты
├── astanga-data.js   — Аштанга-хридая (Вагбхата)
├── ...               — остальные 4 текста
├── encyclopedia.js   — 208 статей
├── glossary.js       — 382 санскритских термина
├── remedies.js       — 113 домашних средств
├── foodtable.js      — 207 продуктов по дошам
├── diseases.js       — 66 болезней
├── quiz.js           — тест пракрити (60 вопросов)
└── cabinet.js        — кабинет эксперта
```

Все данные хранятся прямо в JS-файлах как экспортируемые константы — не отдельные JSON-файлы с fetch, а встроенные структуры. Это упрощает работу офлайн и убирает сетевые запросы при навигации.

## Санскрит: деванагари + IAST

Корректный рендеринг санскрита — отдельная задача. Нужно поддерживать два представления:

1. **Деванагари** — оригинальное письмо (например: `सुश्रुत संहिता`)
2. **IAST** (International Alphabet of Sanskrit Transliteration) — латинская транслитерация с диакритикой: `Suśruta-saṃhitā`

Для деванагари используется шрифт Noto Sans Devanagari, подключённый через Google Fonts. Браузеры в целом справляются с рендерингом деванагари сами, но без правильного шрифта текст выглядит по-разному на разных платформах.

IAST-символы — это Unicode с combining diacritical marks: ā, ī, ū, ṭ, ḍ, ṇ, ś, ṣ, ṃ, ḥ и другие. Здесь главная проблема — поиск. Пользователь вводит «sushruta», а в данных хранится «suśruta». Решение — нормализация при поиске: снимаем диакритику с обеих строк через `normalize('NFD').replace(/[̀-ͯ]/g, '')` и сравниваем латинские основы. Работает для большинства запросов.

Для деванагари поиск по умолчанию отключён — слишком мала вероятность, что пользователь будет вводить текст в деванагари. Но добавить несложно.

## Поиск по 34 тысячам шлоков

Полнотекстовый поиск по такому корпусу без серверного бэкенда — самое интересное место в архитектуре.

Всё решается просто: при загрузке приложения все шлоки из всех JS-модулей уже в памяти. Поиск — это `Array.filter()` с `.includes()` по нормализованной строке. На современном устройстве перебор 34 тысяч коротких строк занимает 20–80 мс — незаметно для пользователя.

Для ускорения добавили debounce на поле ввода (300 мс) и ограничение на вывод первых 100 результатов с ленивой подгрузкой при скролле (Intersection Observer).

Важный момент: поиск работает по русскому переводу, транслитерации IAST и ключевым словам. По деванагари — нет (см. выше). Это покрывает 95% реальных запросов.

## Навигация по длинным главам

Некоторые главы «Чарака-самхиты» содержат 200+ шлоков. Просто выводить весь список — плохо: медленный рендеринг, тяжёлый DOM, неудобная навигация.

Реализована виртуальная пагинация внутри главы: по умолчанию показываются первые 50 шлоков, кнопки «предыдущие»/«следующие» подгружают следующую порцию. DOM при этом перерисовывается целиком для соответствующего «окна» — не настоящий виртуальный скролл, но работает достаточно быстро для текстового контента.

Для навигации между главами — фиксированная боковая панель на desktop и выпадающее меню на mobile. Номер главы и позиция фиксируются в hash, так что прямые ссылки на конкретный шлок работают: `ayurvedareader.ru/#charaka/1/42`.

## PWA и офлайн

Сайт зарегистрирован как Progressive Web App. Service Worker кэширует все JS-файлы с данными после первого посещения — это около 8 МБ суммарно. После этого сайт работает без интернета.

```js
// sw.js — упрощённо
const CACHE = 'ayurveda-v3';
const ASSETS = [
  '/', '/index.html', '/style.css',
  '/charaka-data.js', '/sushruta-data.js',
  '/astanga-data.js', /* ... */
];

self.addEventListener('install', e =>
  e.waitUntil(caches.open(CACHE).then(c => c.addAll(ASSETS)))
);

self.addEventListener('fetch', e =>
  e.respondWith(
    caches.match(e.request).then(r => r || fetch(e.request))
  )
);
```

Стратегия — cache-first для статики, network-first для API (Telegram-бот, кабинет эксперта). При обновлении данных меняем имя кэша — старый удаляется при активации нового SW.

Манифест (`manifest.json`) описывает иконки 192×192 и 512×512, тему, и режим `standalone` — сайт можно установить как приложение на iOS и Android.

## SEO для SPA без SSR

Это главная проблема hash-роутинга с точки зрения SEO. Googlebot умеет выполнять JavaScript, но индексирует `#`-маршруты непредсказуемо — они не создают отдельных страниц в индексе.

Мы решили это комбинацией подходов:

**1. Sitemap.xml с явным перечислением URL.** Для каждой главы, каждой статьи энциклопедии и каждого раздела прописан отдельный URL в sitemap. Файл генерируется скриптом из JS-данных.

**2. JSON-LD разметка.** На каждом «экране» динамически обновляется `<script type="application/ld+json">` с метаданными: название текста, номер главы, автор, язык. Это помогает структурированным данным попадать в поиск даже без полного рендеринга страницы.

**3. Open Graph теги.** `<meta property="og:title">` и `<meta property="og:description">` обновляются при навигации через `document.title` и прямой заменой атрибутов. Для шаринга в соцсетях это работает, потому что превью генерируется при первом открытии ссылки ботом.

**4. Статические мета-страницы.** Для наиболее важных разделов (главная, каждый текст) генерируются статические HTML-файлы с полными метатегами, которые Nginx отдаёт напрямую.

## Деплой: VPS + Nginx + PM2

Сайт хостится на VPS под Ubuntu. Nginx отдаёт статику и проксирует запросы к Node.js-серверу (Express) для кабинета эксперта и API бота.

```nginx
server {
    listen 443 ssl;
    server_name ayurvedareader.ru;

    root /var/www/aurveda;
    index index.html;

    location / {
        try_files $uri $uri/ /index.html;
    }

    location /api/ {
        proxy_pass http://localhost:3001;
    }
}
```

`try_files $uri $uri/ /index.html` — стандартная конфигурация для SPA, возвращающая `index.html` для всех маршрутов. Без этого прямые ссылки и обновление страницы ломаются.

PM2 управляет двумя Node.js-процессами: Express-сервером для API и Telegram-ботом (node-telegram-bot-api). PM2 обеспечивает автозапуск после перезагрузки и мониторинг.

SSL — через Let's Encrypt + Certbot с автообновлением сертификата.

## Что получилось и что нет

**Что работает хорошо:**
- Скорость загрузки: Lighthouse Performance 90+ на десктопе
- Надёжность: нет зависимости от npm-пакетов во runtime, нечему сломаться при обновлении
- Стоимость: один недорогой VPS покрывает всё
- Офлайн-режим после первого посещения

**Что потребовало больше усилий, чем ожидалось:**
- SEO: без SSR это честная борьба, и не всегда выигрышная
- Поддержка больших данных: 8 МБ JS-файлов — это не идеально, хотя и приемлемо
- Обновление данных: нет горячей перезагрузки, каждое изменение — новый деплой

**Что бы сделал иначе:**
Для новых проектов с таким объёмом данных рассмотрел бы SQLite + серверный рендеринг критических страниц. Или Astro с частичной гидратацией. Но для данного проекта решение оказалось достаточным — и работает.
