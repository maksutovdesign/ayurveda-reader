# Кабинет экспертов — архитектура

Цель: эксперты входят через Telegram, предлагают правки/переводы глав и стихов,
администратор одобряет. Одобренные правки накладываются поверх статических данных книг.

## Принципы

1. **Аддитивность.** Статический сайт работает как раньше, даже если бэкенд/БД недоступны.
   Правки — это слой «overrides» поверх базовых данных в JS-файлах.
2. **Без паролей.** Авторизация через Telegram Login Widget (переиспользует существующего бота).
   Подпись проверяется на сервере по BOT_TOKEN (HMAC-SHA256).
3. **Stateless-сессии.** После входа сервер выдаёт подписанный токен (HMAC по BOT_TOKEN),
   хранится в localStorage. Никакого стороннего хранилища сессий.

## Роли

| Роль | Кто | Права |
|------|-----|-------|
| Гость | не вошёл | чтение |
| Пользователь | вошёл через Telegram | чтение + может предложить правку |
| Эксперт | tgId в наборе `experts` (KV) или `EXPERT_TG_IDS` | правки помечаются доверенными |
| Админ | tgId в `ADMIN_TG_IDS` (env) | одобрение/отклонение правок, управление экспертами |

## Хранилище — Vercel KV (Upstash Redis)

Ключи:
- `proposal:<id>` — объект правки `{id,tgId,tgName,bookId,sthana,chapter,verseNumber,field,oldValue,newValue,comment,status,createdAt}`
- `proposals:pending` — список id ожидающих
- `proposals:all` — список всех id
- `override:<bookId>:<sthana>:<chapter>:<verseNum>:<field>` — одобренное значение (живой слой)
- `experts` — набор tgId экспертов

## API (Vercel serverless)

- `POST /api/auth-telegram` — принимает payload Telegram Login, проверяет hash, возвращает сессионный токен
- `GET  /api/overrides?book=<id>` — одобренные правки книги (для наложения на статику)
- `GET  /api/proposals` — (админ) список ожидающих правок
- `POST /api/proposals` — (пользователь/эксперт) создать правку
- `POST /api/proposals/review` — (админ) одобрить/отклонить
- `GET  /api/entitlements` — права текущего пользователя + каталог товаров + флаги (paymentsEnabled, contentProtection, testLogin)
- `POST /api/pay-create` / `POST /api/pay-webhook` / `POST /api/sub-cancel` — оплата (YooKassa)
- `POST /api/proposals` (kind:'article') — заявка на новую статью (энциклопедия/глоссарий/средства)
- `GET  /api/overrides?collection=encyclopedia|glossary|remedies` — одобренные статьи сообщества (наложение)
- `GET  /api/health` — диагностика активации: что настроено (только булевы флаги/счётчики, без секретов)
- `POST /api/auth-telegram` {mode:'dev'} — тестовый вход с полным доступом, **только при `TEST_LOGIN=1`** (иначе 404)

> Примечание: эндпоинты `articles` и `dev-login` объединены в `overrides` и `auth-telegram`
> соответственно, чтобы уложиться в лимит Vercel Hobby — **не более 12 serverless-функций**.

Все эндпоинты деградируют мягко: если KV не настроен — возвращают пустой результат/ошибку,
фронтенд продолжает работать на статических данных.

## Настройка на Vercel (делает владелец)

1. Vercel → Storage → создать **KV** (Upstash Redis), привязать к проекту
   (автоматически добавит `KV_REST_API_URL`, `KV_REST_API_TOKEN`).
2. Env vars:
   - `ADMIN_TG_IDS` = ваш Telegram user id (узнать у @userinfobot), через запятую
   - `EXPERT_TG_IDS` = (опц.) стартовый список экспертов
   - `BOT_TOKEN` — уже есть (используется для проверки Telegram Login)
3. У бота в @BotFather: `/setdomain` → указать домен сайта (для Telegram Login Widget).

## Монетизация (YooKassa)

Модель (настраивается в `lib/pricing.js`):
- **Аштанга-хридая — бесплатна** (флагман). Остальные книги — платные.
- Товары: отдельная книга, полный доступ навсегда, пропуск на 30 дней.
- Первые `PREVIEW_CHAPTERS` глав платной книги открыты для ознакомления.
- «Подписка» = пропуск на N дней (разовый платёж, без авто-списаний).

Поток оплаты:
1. Пользователь (вошедший) жмёт «Купить» → `POST /api/pay-create`
2. Бэкенд создаёт платёж в YooKassa → возвращает `confirmation_url` → редирект
3. После оплаты YooKassa шлёт `POST /api/pay-webhook`
4. Вебхук **перепроверяет статус** напрямую у YooKassa (защита от подделки) → выдаёт права (`ent:<tgId>` в KV)
5. Фронт по `GET /api/entitlements` узнаёт доступ и снимает paywall

Важно: paywall показывается **только если** `YOOKASSA_*` заданы (иначе сайт открыт).
Контент сейчас в статических JS — гейтинг «мягкий» (превью + paywall). Жёсткая
защита (отдача платного контента из API) — отдельный следующий шаг.

### Доп. настройка для платежей (Vercel)
- `YOOKASSA_SHOP_ID`, `YOOKASSA_SECRET_KEY` — из личного кабинета YooKassa
- В YooKassa: webhook на `https://<домен>/api/pay-webhook`, событие `payment.succeeded`
- Требуется самозанятость/ЮЛ для договора с YooKassa

## Этап 6 — жёсткая защита контента (как активировать)

Механизм готов и работает под флагом. Когда выключен — сайт грузит статические
файлы (мягкий paywall, как сейчас). Когда включён — данные платных книг отдаются
только через `/api/book-data` с проверкой прав; без прав приходит лишь превью.

Чтобы активировать на платном хостинге:

1. **Env:** `CONTENT_PROTECTION=1` (+ должны быть настроены KV и YOOKASSA для прав).
   Фронт получает флаг через `/api/entitlements` и переключает загрузку книг на API.

2. **Заблокировать прямой доступ к статическим данным платных книг.** Иначе их можно
   скачать напрямую. Добавьте в `vercel.json` (раздел `rewrites` или `routes`)
   возврат 404 для платных `*-data.js`, например через rewrites на функцию-заглушку,
   ИЛИ вынесите эти файлы из публичной выдачи. Серверные функции импортируют их
   на сборке (бандл), поэтому HTTP-блокировка не ломает `/api/book-data`.
   Файл `data.js` (бесплатная Аштанга-хридая) НЕ блокировать.

3. Проверить: неавторизованный запрос `/api/book-data?book=charaka` возвращает
   `entitled:false` и только превью-главы; авторизованный с правами — полный текст.

Замечание: абсолютной защиты клиентского контента не существует (платящий
пользователь технически может извлечь то, что ему отдали). Но это закрывает
прямое скачивание неоплаченного контента — то, чего не было при мягком paywall.

## Активация на платном хостинге — чеклист

Сайт полностью работает и без настройки (статика). Ниже — что включить, чтобы
заработали кабинет, оплата и т.д. Все шаги с аккаунтами/секретами выполняет владелец.

1. **Кабинет экспертов + краудсорс-перевод** (нужны `BOT_TOKEN` + KV):
   - Vercel → Storage → создать **KV (Upstash Redis)**, привязать к проекту
     (добавит `KV_REST_API_URL`, `KV_REST_API_TOKEN`). Upstash имеет бесплатный тариф.
   - `BOT_TOKEN` — токен бота (уже используется ботом). Хранить только в env Vercel и `bot/.env`.
   - `ADMIN_TG_IDS` — ваш Telegram id (узнать у @userinfobot), через запятую.
   - `WEBHOOK_SECRET` — случайная строка для защиты вебхука бота.
   - @BotFather → `/setdomain` → домен сайта (для Telegram Login Widget).

2. **Бот: посты в канал** (нужны `BOT_TOKEN` + `CHANNEL_ID` + `DAILY_POST_KEY`):
   - `CHANNEL_ID` — id/username канала, бот должен быть админом канала.
   - `DAILY_POST_KEY` — секрет, которым крон дёргает `/api/daily-post`.
   - На бесплатном Vercel — максимум 2 крона (уже заняты постами 09:00 и 18:00 UTC).

3. **Монетизация** (нужны `YOOKASSA_*` + KV):
   - `YOOKASSA_SHOP_ID`, `YOOKASSA_SECRET_KEY` — из ЛК YooKassa (нужна самозанятость/ЮЛ).
   - В YooKassa: webhook на `https://<домен>/api/pay-webhook`, событие `payment.succeeded`.
   - Paywall появляется ТОЛЬКО когда заданы `YOOKASSA_*` — иначе сайт открыт.

4. **Авто-продление подписки** (Этап 7): требует **Vercel Pro** (на Hobby лимит 2 крона
   и ≤12 функций). Эндпоинт `api/renew-subscriptions.js` был удалён ради лимита Hobby —
   при переходе на Pro восстановить его из истории git и добавить 3-й крон в `vercel.json`.

5. **Жёсткая защита контента** (Этап 6): `CONTENT_PROTECTION=1` + блокировка прямой
   отдачи платных `*-data.js` (см. раздел выше).

После настройки откройте **`/api/health`** — он покажет, что включилось, и предупредит
о проблемах (например, оплата без KV). Значения секретов не раскрываются.

### Справочник переменных окружения

| Переменная | Зачем | Без неё |
|------------|-------|---------|
| `BOT_TOKEN` | Telegram-логин (подпись) + бот | нет входа через Telegram (но тест-вход и статика работают) |
| `SESSION_SECRET` | подпись сессий, если нет `BOT_TOKEN` | используется дев-значение (только для локали) |
| `KV_REST_API_URL`, `KV_REST_API_TOKEN` | хранилище правок/прав | правки/оплата не сохраняются, сайт на статике |
| `ADMIN_TG_IDS` | роль админа (модерация) | некому одобрять правки |
| `EXPERT_TG_IDS` | стартовые эксперты | правки от всех «пользовательские» |
| `YOOKASSA_SHOP_ID`, `YOOKASSA_SECRET_KEY` | приём оплаты | paywall выключен, всё открыто |
| `CHANNEL_ID` | канал для постов бота | бот не постит в канал |
| `DAILY_POST_KEY` | защита `/api/daily-post` | крон не может вызвать пост |
| `WEBHOOK_SECRET` | защита вебхука бота | вебхук без проверки секрета |
| `CONTENT_PROTECTION` | жёсткая защита (Этап 6) | мягкий paywall (превью) |
| `TEST_LOGIN` | тест-вход с полным доступом | тест-кабинет недоступен (норма для прода) |
| `TEST_FULL_TG_IDS` | реальные id с полным доступом для теста | — |

## Тестовый кабинет (TEST_LOGIN)

Чтобы протестировать кабинет/перевод/полный доступ без полной продовой настройки:

- Установите `TEST_LOGIN=1` в env (например, на превью-деплое или локально).
- В разделе «Кабинет» появится кнопка **«🧪 Тест-вход (полный доступ)»**
  (роль admin + доступ ко всем книгам). На localhost кнопка есть всегда.
- На сервере с `TEST_LOGIN=1` это реальная сессия (полный воркфлоу, нужен KV для правок);
  на статике без бэкенда — локальная фейк-сессия (UI/доступ, модерация недоступна).
- `TEST_FULL_TG_IDS` (через запятую) — дать полный доступ конкретным реальным Telegram-id
  (тоже только при `TEST_LOGIN=1`), удобно для своего аккаунта.

> ⚠️ **Безопасность:** НЕ включайте `TEST_LOGIN` на публичном проде — это обходит оплату
> и выдаёт права администратора. По умолчанию dev-вход (`auth-telegram` {mode:'dev'}) отвечает 404, а кнопка скрыта.
> Проверить можно через `/api/health` (поле `features.testLogin` и предупреждение).
